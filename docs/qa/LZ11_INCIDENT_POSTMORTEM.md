# ЛЗ 11 — разбор реального инцидента в тестировании

**Инцидент:** LZ11-INC-01. **Тип:** дефект тестовой подготовки CSRF после входа в систему. **Источник:** реальные журналы тестов ЛЗ 9, сохранённые в `docs/lz9-card13-20/evidence/`. **Дата:** 14 ноября 2026 года. **Статус:** исправлен в ЛЗ 9; дополнительные меры проверки добавлены в ЛЗ 11.

## Что произошло

При первом запуске набора тестов V3 **5 из 90 тестов не прошли**. В тестовом клиенте после успешной авторизации выполнялся запрос, ожидавший существующий CSRF-токен, однако токен отсутствовал. Ошибка имела вид `KeyError: 'csrf_token'`. В логе встречается в `test_mock_fetch_and_scoring`, `test_mock_offline_message`, `test_upload_per_row_results`, `test_upload_unknown_columns_rejected` и `test_csrf_and_login_required`.

Это **сбой автоматизированной приёмки**, а не установленный факт отказа приложения для реальных пользователей. Тестовое окружение синтетическое. Не следует использовать его для подсчёта доступности работающего клинического сервиса.

## Измеримое влияние

- Затронуты **5 автоматических тестов из 90** на первом запуске, то есть 5,6 % сценариев были заблокированы.
- В первом логе обнаружено **0 зарегистрированных ошибок процесса тестирования**, но 5 тестовых failures.
- Подтверждённые реальные пострадавшие пользователи: **не выявлены**; проект был учебным локальным стендом.
- Потерянные реальные медицинские операции: **не зафиксированы**.
- Время простоя работающего сервиса и MTTR: **неизвестны и неприменимы** по данным этого инцидента.

## Системные факторы без поиска виноватых

1. Успешный вход намеренно очищает анонимную сессию и вместе с ней прежний CSRF-токен; при дальнейших действиях нужно получить новый токен из следующей формы.
2. Первоначальная тестовая фикстура не открывала новую форму после входа и ожидала несуществующий ключ в сессии.
3. До обнаружения дефекта не было выделенного регрессионного сценария, проверявшего весь цикл «вход → новый CSRF → действие с формой».
4. Сам факт появления зелёного HTTP-ответа страницы входа не гарантирует, что последующие действия с формами работают.

## Что сработало

- pytest быстро выявил повторяемую ошибку и названия пяти затронутых сценариев.
- Сохранённые XML и журналы позволили точно сопоставить первый провал и последующий успешный запуск.
- Изменение фикстуры было небольшим и проверено повторной регрессией, без изменения механизма CSRF для пользователей.
