# ЛЗ 11 — стратегия и план тестирования «КардиоПрогноз»

**Объект:** приложение `CardioPrognoz_V3/` (Flask, локальная SQLite для учётных записей, учебная ML-модель). **Статус:** план и самостоятельный HTTP-прогон 13 сценариев готовы; независимая пользовательская приёмка ожидается. **Дата плана:** 2026-11-20, уточнение 2026-11-24.

## 1. Цель и границы

Проверить, что учебный сайт позволяет безопасно войти, рассчитать вероятность класса заболевания на синтетических показателях, получить понятную ошибку при неверных данных, проверить тестовый импорт из mock-МC и CSV. Это **не** медицинская сертификация, оценка диагностической пригодности или разрешение обработки реальных медицинских данных.

В версии 3 **нет** сохранения истории пациентов, экспорта в PDF, функции «отклонить с причиной» и реального подключения к клинической МИС. Эти функции нельзя отмечать проверенными. Запрет доступа к чужим сохранённым пациентским записям пока неприменим; вместо него в текущем объёме проверяется запрет обычному пользователю открывать административный раздел.

## 2. Стратегия тестирования

| Уровень | Плановая доля усилий | Что проверяет | Инструмент | Когда запускается |
|---|---:|---|---|---|
| Модульный | 35 % | Нормализация 13 полей, правила импорта, пароль, генератор данных | pytest | При каждом PR и локально |
| Интеграционный | 25 % | Flask + SQLite, CSRF, mock API, CSV-импорт | pytest + Flask test client | При каждом PR |
| Сквозной | 20 % | Вход → экран → расчёт → выход; импорт и сообщения | pytest (автоматизация маршрутов), ручной браузер | При PR и перед приёмкой |
| Нагрузочный | 10 % | Время ответа при одновременных запросах на учебном стенде | k6 | При изменении кода/сценария, перед релизом |
| Ручной и UAT | 10 % | Ясность интерфейса и самостоятельность пользователя | сценарии и протокол UAT | Независимый пользователь до закрытия ЛЗ |

Доли относятся к **плану времени**, а не к фактически измеренному количеству тестов. Сквозные проверки браузером через Playwright можно добавить отдельным этапом; существующие тесты Flask не выдают себя за проверку реальным браузером.

## 3. Тестовые данные и воспроизводимость

Все 13 полей исходят из локальных синтетических записей `SYN-001`…`SYN-020`. Генератор использует `random.Random(seed)` и фиксированное начальное зерно **11011**. С одинаковыми параметрами результат побайтно совпадает.

```bash
cd CardioPrognoz_V3
python qa_data.py --output samples/lz11_synthetic_50.csv --seed 11011
```

Создаётся 50 строк, из них 45 корректных и 5 с намеренно неверным возрастом; ошибочные **строки файла 11, 21, 31, 41, 51**. Скрипт не читает реальные данные. Поля ФИО, паспорт, email, телефон отсутствуют. Проверять отсутствие этих полей в экспортируемом CSV обязательно; файлы SQLite с аккаунтами в GitHub не публиковать.

## 4. Среды

| Среда | Назначение | Данные | Кто разворачивает | Текущий факт |
|---|---|---|---|---|
| Локальная | Разработка, воспроизведение дефекта | Синтетические | Разработчик | Используется |
| Проверка PR в CI | Автотесты и временный контейнер | Синтетические | GitHub Actions | Реализована в ЛЗ 10 |
| Предпродуктивная постоянная | Репетиция UAT и эксплуатации | Только согласованные тестовые | Назначенный ответственный | Не создана |
| Рабочая | Реальные пользователи после разрешений | Определит заказчик | Администратор организации | **Отсутствует**; клинический выпуск запрещён |

Временный CI-контейнер исчезает после задания — это **не** постоянно доступный сервер. Нагрузочные тесты выполняют только в изолированной среде, никогда на реальном клиническом сервисе.

## 5. Проверяемые количественные требования

| Идентификатор | Проверяемое требование | Сценарий | Статус основания |
|---|---|---|---|
| НФТ-18 | 20 последовательных корректных обменов с тестовой МИС | существующий `test_nft18_twenty_real_http_requests` | Уже отмечено в критериях CARD-19 ЛЗ 9 |
| НФТ-19 | 45 корректных + 5 ошибочных строк в импорте 50 строк | `test_45_valid_and_5_invalid_synthetic_rows` и существующий тест CARD-20 | Уже отмечено в критериях CARD-20 ЛЗ 9 |
| LZ11-NFR-01 | GET страницы входа: 30 одновременных пользователей; **p95 < 1000 мс**, ошибки < 1 % | `tests/load/login.js` | **Предлагаемый порог**, согласовать с заказчиком/НФТ ЛЗ 4 |
| LZ11-NFR-02 | Авторизованный расчёт: 5 одновременных пользователей; **p95 < 1500 мс**, успешные проверки > 99 % | `tests/load/predict.js` | **Предлагаемый порог**, согласовать с заказчиком/НФТ ЛЗ 4 |

В текущем репозитории не найден подтверждённый отдельный документ с количественными порогами времени ответа из ЛЗ 4. Поэтому два порога k6 — **не заявленные задним числом требования ЛЗ 4**, а предложения, которые необходимо сверить с оригиналом ЛЗ 4. Даже успешный тест не означает, что заказчик утвердил эти границы.

Запуск на машине с установленными k6 и работающим стендом:

```bash
BASE_URL=http://127.0.0.1:8000 k6 run tests/load/login.js
BASE_URL=http://127.0.0.1:8000 K6_USER=synthetic_qa K6_PASSWORD=<test-only-password> k6 run tests/load/predict.js
```

В GitHub Actions это выполняется на одноразовом контейнере с одноразовой учётной записью, созданной специально для теста. Для интерпретации p95 нужно читать реальный лог k6 из артефакта workflow, а не примерную цифру из плана.

## 6. Управление дефектами

| Приоритет | Пример | Предлагаемый срок реакции/исправления | Влияние на приёмку |
|---|---|---|---|
| Блокирующий P0 | Утечка данных, доступ к чужим учетным записям, невозможен вход для всех | Реакция до 1 ч; устранить до выпуска | Приёмка запрещена |
| Высокий P1 | Корректная форма постоянно не рассчитывает прогноз | Реакция за рабочий день; исправить до 2 дней | Приёмка блокируется |
| Средний P2 | Ошибка отдельной операции с обходным путём | Реакция до 2 дней; исправить до 5 рабочих дней | По согласованию заказчика |
| Низкий P3 | Косметическое сообщение или отступ | Реакция до 5 дней; в ближайший спринт | Не блокирует приёмку |

Сроки — проектные правила, пока не согласованные заказчиком. Каждый дефект фиксируется в GitHub Issue: шаги, ожидаемый/фактический результат, окружение, приоритет, владелец, срок, ссылку на подтверждение. В журнал, issue и CI не помещать медицинские данные пациентов.

## 7. Мониторинг, вход и выход из тестирования

- Наличие доступной страницы `GET /login` проверяется HTTP-мониторингом; ручная инструкция для Uptime Kuma приведена в `docs/ops/LZ11_MONITORING.md`.
- До начала: тестовый контейнер запускается, модель доверенная, база содержит только временные учётные записи, набор данных синтетический.
- Успех: все критичные pytest-тесты зелёные; k6 соблюдает утверждённые пороги либо отклонение зарегистрировано; нет открытых P0/P1; сценарии независимого UAT реально выполнены.
- Неподтверждённые результаты отмечать «не проверено», а не «пройдено».
