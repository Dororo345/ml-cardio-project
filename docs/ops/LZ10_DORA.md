# ЛЗ 10 — определения DORA, методика и ограничения

Дата: 2026-11-16. Проект: `Dororo345/ml-cardio-project`. Источник: GitHub Deployments API + отдельный журнал инцидентов.

## 4 метрики (скрипт scripts/dora.py)
1. **Deployment Frequency** — число успешных deployment statuses в `lz10-ci-staging` за последние 30 дней / (30/7) = развёртываний в неделю. Зелёный CI **не** является развёртыванием.
2. **Lead Time for Changes** — медиана часов от даты коммиттера связанного SHA до даты успешного статуса deployment в данном окружении. Не равно времени цикла от первого кода до релиза; выбрана воспроизводимая упрощённая прокси-метрика. Если нужных записей нет — N/A.
3. **Change Failure Rate** — 100 × deployments с итоговым статусом failure/error / (success + failure/error). Система автоматически видит только неудавшиеся deployment statuses, не все дефекты после выпуска. Запоздалые сбои должны фиксироваться вручную в журнале инцидентов, формула расширяется после появления связей с deployment ID.
4. **Time to Restore Service** — медиана часов между `started_at_utc` и `restored_at_utc` у **реально зарегистрированных и закрытых** инцидентов в `docs/ops/INCIDENTS.csv`. Нет инцидентов — N/A (не 0).

Отдельно считаем `repair_hours` — трудозатраты на исправления (не то же самое, что длительность восстановления). Все времена UTC. Данные вне окна игнорируются. Пороговых категорий DORA без достаточной истории не присваиваем: уровень обозначается «данных недостаточно».

### Запуск
```bash
python -m pip install matplotlib
# локально: установить GH_TOKEN через переменную окружения (не сохранять в git)
python scripts/dora.py --repo Dororo345/ml-cardio-project --days 30 --environment lz10-ci-staging
```
Выход: `lz10-results/dora.json`, `lz10-results/deployments.csv`, `lz10-results/dora_dashboard.png`. В GitHub Actions эти файлы публикуются как artifact при успешном `main`-прогоне.

### Интерпретация и меры
- Улучшение 1: после каждого PR в `main` запускать автоматическое staging-развёртывание; **целевое** значение частоты: минимум 1 за неделю при наличии изменений. Проверить повторно **2026-12-14**.
- Улучшение 2: ограничить время pipeline до 10 минут, добавить smoke + обязательное покрытие 50%; **целевой** lead time — менее 1 часа от коммита до CI-staging при успешном выпуске. Проверить повторно **2026-12-14**.
- Целевые значения — инженерные ориентиры, **не реальные наблюдения и не обещания**.
- Предложение по надёжности: 15% недельной capacity до появления эмпирических `repair_hours`; пересчёт 2026-12-14.

### Проверки методики
- Проверять состояния GitHub Deployment, а не количество успешных Actions.
- `lz10-ci-staging` — эфемерный контейнер на GitHub runner; не указывать как рабочую систему для пациентов.
- Если нет истории, явно показывать N/A. Не создавать фиктивных инцидентов.
- Нельзя класть Fine-grained PAT, персональные или клинические данные в CSV, логи или репозиторий.
- Изменения правил защиты main требуют админ-доступа GitHub и отдельной проверки на красном PR.
