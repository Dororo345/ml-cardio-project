# ЛЗ 10 — определения метрик DORA, измерение и ограничения

Проект: КардиоПрогноз, `Dororo345/ml-cardio-project`. Методика актуализирована 16.11.2026. Все текущие наблюдения относятся только к временному учебному контейнеру `lz10-ci-staging`, не к медицинской или продуктивной системе.

## Что считается развёртыванием
Одно GitHub Deployment в окружении `lz10-ci-staging`, для которого зарегистрирован итоговый статус `success`, `failure` или `error`. Запуск Actions или проверка pull request без GitHub Deployment не считаются релизом. После успешного job тестовый контейнер удаляется.

## Четыре метрики
1. **Deployment Frequency (DF):** число успешных GitHub deployments за 30 дней / (30/7), развёртываний в неделю.
2. **Lead Time for Changes (LT):** медиана времени между датой committer SHA и успешным статусом связанного развёртывания. Это упрощённый заменитель полного времени от первой строки кода до поставки, а не точный показатель полного change lead time.
3. **Change Failure Rate (CFR):** 100% × число **уникальных завершённых развёртываний** с негативным исходом / число всех завершённых deployments (`success`, `failure`, `error`). Изменение считается неудачным при: (а) статусе deployment `failure`/`error`; **или** (б) статусе `success`, после которого в течение 24 часов зарегистрирован связанный инцидент, потребовавший `fix` или `rollback`. Одна запись deployment считается **один раз**, даже если инцидентов несколько. Не связанный с конкретным deployment или зарегистрированный позже 24 часов инцидент не приписывается автоматически: он учитывается отдельно для разбора.
4. **Time to Restore (TTR):** медиана времени от фактического начала до фактического завершения восстановления зарегистрированных инцидентов. Если таких нет, значение N/A. Время исправления в человеко-часах (`repair_hours`) измеряется отдельно.

## Учёт инцидентов
Сведения вводятся только по факту в `docs/ops/INCIDENTS.csv`. Заголовки:
```csv
incident_id,started_at_utc,restored_at_utc,linked_deployment_id,remediation_action,repair_hours,description
```
- `linked_deployment_id` — точный GitHub Deployment ID. Пустой ID не позволяет достоверно приписать сбой изменению.
- `remediation_action` — только `fix` или `rollback` для классификации CFR; другую причину оставляют вне классификации и исследуют отдельно.
- Время — UTC ISO 8601. Регистрация должна быть полной, иначе CFR может быть занижен.
- Если нет фактов, не создавайте ложные инциденты и не заявляйте достоверный нулевой уровень отказов.

## Два системных улучшения
- Автоматическое staging-развёртывание после слияния в main; цель — ≥1 успешное развёртывание в неделю при наличии изменений. Пересчёт **14.12.2026**.
- Обязательные CI checks, pytest coverage 50%, gitleaks, Docker smoke и цель pipeline ≤10 минут; ориентир LT от коммита до staging <1 часа. Пересчёт **14.12.2026**.

Указанные цели — план, а не измеренный эффект. Предварительная доля capacity под исправления — 15%, после накопления реальных repair_hours пересчитать 14.12.2026.

## Воспроизведение
```bash
python -m pip install matplotlib
python -m pytest -q tests/test_lz10_dora.py
# После установки GH_TOKEN локально; в Actions используется GITHUB_TOKEN:
python scripts/dora.py --repo Dororo345/ml-cardio-project --environment lz10-ci-staging --days 30
```
Артефакты: `lz10-results/dora.json`, `deployments.csv`, `dora_dashboard.png`. В CI они публикуются как `lz10-dora-dashboard` после успешного main push. Для локального токена требуются права чтения репозитория и deployments. Никогда не записывайте токены, пароли, личные/медицинские данные в Git.

Метрика CFR пригодна для содержательных выводов **только при полноценном учёте пострелизных инцидентов**. Небольшая выборка и временность стенда — ключевые ограничения.
