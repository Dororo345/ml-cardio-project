# ЛЗ 11 — runbook восстановления учебного сайта КардиоПрогноз

**Сценарий:** страница входа перестала открываться или пользователь не может выполнять действия после входа. **Область:** локальный V3 и временный Docker-стенд CI. Для клинической эксплуатации инструкция не утверждена.

## Признаки и первоначальные проверки

- Браузер показывает ошибку подключения к сайту или `/login` не отвечает HTTP 200.
- После входа форма интеграции выдаёт ошибку о CSRF, хотя токен пришёл из новой формы.
- Автоматические `LZ11 synthetic load testing`, `CardioPrognoz V3 acceptance`, `LZ10 quality` в GitHub Actions стали красными.

**Первый шаг:** записать время UTC, версию (`git rev-parse --short HEAD`), адрес тестового стенда и наблюдаемое сообщение. Не копировать реальные медицинские показатели или пароли в Issue.

## Диагностика на локальном Windows PowerShell

В каталоге `CardioPrognoz_V3`:

```powershell
python --version
python -m flask --app app routes
curl.exe -i http://127.0.0.1:5000/login
python -m pytest -q tests/test_lz11_quality.py
```

Если первый HTTP-запрос не даёт 200, убедиться, что Flask действительно запущен, а порт 5000 не занят другим приложением:

```powershell
netstat -ano | findstr :5000
python app.py
```

Если не работает логин, проверить наличие базы учётных записей `instance/cardio.sqlite3` **локально**, не прикладывая её к переписке или Issues. Восстанавливать тестовую базу только из своей резервной копии либо создавать заново лишь в полностью disposable-окружении. Команда `init-db` не удаляет существующую таблицу, но не восстанавливает потерянные учётные записи.

```powershell
python -m flask --app app init-db
```

## Диагностика временного Docker-стенда на Linux CI

```bash
docker ps --filter name=cardio-lz11
docker logs --tail 100 cardio-lz11
curl -i --max-time 5 http://127.0.0.1:8000/login
docker exec cardio-lz11 python -m flask --app app routes
```

Проверить в логах отдельные признаки: не загрузилась модель, отсутствует SQLite, сервер не слушает порт, форма отвергает CSRF после авторизации. Не публиковать дамп базы, переменные окружения с паролями и сырые медицинские показатели.

## Восстановление

1. При проблеме зависимостей или модели откатить **одноразовый тестовый стенд** на ранее проверенный SHA/образ. Перед откатом сохранить ссылку на неудачную сборку; production-трафика здесь нет.
2. При проблеме запуска восстановить совместимые зависимости из `requirements.txt`, затем перезапустить сервис и проверить HTTP `/login`.
3. При CSRF после входа открыть страницу `/integration` заново, чтобы получить новый токен; если ошибка сохраняется, сохранить статус теста и остановить выпуск, не отключать защиту CSRF.
4. При недоступности mock-сервиса запустить его локально `python mock_medical_service.py` (порт 5001) или проверить ожидаемое сообщение об отсутствии mock. Не подключать настоящую МИС вместо тестового сервиса.
5. Повторить `pytest` и сценарии `UAT-01`, `UAT-11`, `UAT-13` на **синтетических** аккаунтах и данных.
6. Зафиксировать время восстановления, результаты и номер GitHub Issue; для незакрытой проблемы оставить метку «не готово к выпуску».

Временный CI-стенд удаляется после задачи, поэтому для него допустимо остановить и создать контейнер заново. Для постоянного или рабочего стенда нужен отдельный согласованный план резервного копирования и миграций; применить команды удаления базы к нему нельзя.

|---|---|---|

| Ответственный за релиз | **Нужно назначить** | До отката или слияния PR с критическим дефектом |
| Преподаватель / независимый проверяющий | Контакт согласовывает студент | Если требуется приёмка, отсутствует доступ к стенду или нет полномочий изменять настройки |

**Проектное правило:** P0 — уведомить ответственного немедленно, решение об остановке выпуска в течение 5 минут после подтверждения; целевое восстановление тестового стенда в 15 минут. Это **плановые цели**, а не достигнутые SLA. Если ответственный за выпуск не назначен, не выполнять непроверенный продакшн-откат.

## Независимая проверка инструкции

**Пока не проведена.** Другой студент получает эту инструкцию без дополнительных пояснений и должен зафиксировать дату, своё имя/команду, проверенные команды, время от первого шага до успешного `/login` и непонятные места. Эти сведения вносить в протокол UAT или отдельную запись GitHub Issue. Самостоятельная проверка разработчиком не заменяет этот пункт методички.
